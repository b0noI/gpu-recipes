# Goodput Measurement Migration - Testing Plan

## 1. Introduction

The purpose of this document is to outline the testing strategy for migrating from the old goodput logging mechanism to the new `ml-goodput-measurement` library, specifically focusing on the `GoodputRecorder` integration and the `new_goodput_calculator_cli.py` script. This plan aims to ensure the new system accurately captures and processes goodput-related events.

## 2. Unit Tests for `ml-goodput-measurement` Library

**Objective:** Verify the core functionality of the `ml-goodput-measurement` library itself, including `GoodputRecorder` and `GoodputCalculator`.

**Actions:**
1.  **Locate Unit Tests:** Identify the existing unit test suite within the `ml-goodput-measurement` library's source code.
2.  **Execute Tests:** Run all unit tests for the library.
    *   Command (example): `python -m unittest discover -s tests/ -p 'test_*.py'` (or the specific command used by the library, e.g., `pytest`).
3.  **Verify Outcomes:**
    *   All existing unit tests for `GoodputRecorder`, `GoodputCalculator`, and related utility functions should pass.
    *   Ensure test coverage is adequate for the new components and changes, if any were made to the library itself during this migration.

**Success Criteria:** All library unit tests pass without errors.

## 3. Integration Testing of `GoodputRecorder`

**Objective:** Ensure `GoodputRecorder` is correctly integrated into training scripts and that events are logged as expected.

**Prerequisites:**
*   A training script instrumented with `GoodputRecorder` as per the `GoodputRecorder_Integration_Guide.md`.
*   Access to the backend where these logs/events are stored (e.g., specific log files, a database, or a logging platform like BigQuery).

**Actions:**
1.  **Run Instrumented Training Script:** Execute a short training run (or a few variations) using a script that has `GoodputRecorder` integrated.
    *   Ensure the script triggers all relevant events: `user_scheduled`, `job_started`, `tpu_init_started`, `tpu_init_completed`, `training_prep_started`, `training_prep_completed`, `data_loading_started`, `data_loading_completed`, `step_started`, `step_completed` (for several steps), `checkpoint_saved` (if applicable), `checkpoint_loaded` (if applicable), and `job_terminated`.
    *   Simulate different termination statuses if possible (e.g., `COMPLETED`, `FAILED`).
    *   Trigger a `custom_badput_event` if feasible within the test script.

2.  **Inspect Raw Event Logs:**
    *   Access the raw event data generated by `GoodputRecorder`. This might involve:
        *   Checking specific log files if `GoodputRecorder` is configured to output to local files for testing.
        *   Querying a database or logging platform (e.g., BigQuery) using the `run_key` or `logger_name` associated with the test run.
    *   **Verify for each logged event:**
        *   **Correct Event Name:** The event name matches the method called (e.g., `job_started` method logs a "JOB_STARTED" event).
        *   **Accurate Timestamps:** Timestamps are present and plausible (e.g., `job_started` timestamp is after `user_scheduled`).
        *   **Presence of Metadata:** All relevant metadata is included and correct (e.g., `step_number` for step events, `path` for checkpoint events, `status` and `details` for `job_terminated`).
        *   **Correct `run_key` / `logger_name`:** Ensure events are associated with the correct identifier.

3.  **Sequence Verification:**
    *   Check that the sequence of critical events is logical (e.g., `tpu_init_started` before `tpu_init_completed`, `step_started` before `step_completed`).

**Success Criteria:**
*   The instrumented training script runs without errors related to `GoodputRecorder`.
*   All intended events are logged with correct names, timestamps, and metadata.
*   The sequence of logged events is logically correct.

## 4. Testing `new_goodput_calculator_cli.py`

**Objective:** Verify that the `new_goodput_calculator_cli.py` script correctly fetches data logged by `GoodputRecorder`, performs calculations, and displays the results accurately.

**Prerequisites:**
*   Successful completion of Integration Testing for `GoodputRecorder`, ensuring test event data exists in the backend.
*   The `new_goodput_calculator_cli.py` script.
*   The `ml-goodput-measurement` library (including `GoodputCalculator`) installed or available in `PYTHONPATH`.

**Actions:**
1.  **Execute CLI with Valid `job_name`:**
    *   Run `new_goodput_calculator_cli.py` using the `job_name` (or `logger_name`) from a completed integration test run.
    *   Command (example): `python new_goodput_calculator_cli.py --job_name "test_job_run_001"`

2.  **Verify CLI Output:**
    *   **Goodput Percentage:** Check if the calculated goodput percentage is reasonable given the events logged. For a simple test run with minimal simulated badput, this should be high.
    *   **Badput Breakdown:**
        *   If badput events were logged (or if there are expected gaps like TPU initialization), ensure the breakdown reflects these sources.
        *   Verify that the percentages in the breakdown sum to approximately 100% of the total badput.
    *   **Job Timeline Information:**
        *   `Job Start Time`, `Job End Time`: Match these against the timestamps logged by `GoodputRecorder` for `job_started` and `job_terminated`.
        *   `Last Step Number`, `Last Step Time`: Match these against the latest `step_completed` event.
    *   **Total Times:** Ensure `Total Goodput Time`, `Total Badput Time`, and `Total Measured Duration` are consistent with each other (`Goodput + Badput = Measured Duration`).

3.  **Test with Different Scenarios (if applicable):**
    *   Run CLI for a job that failed (ensure `job_terminated` status was 'FAILED').
    *   Run CLI for a job with known significant badput (e.g., long `TPU_INIT` time or many `custom_badput_event`s). Observe the impact on goodput percentage and breakdown.
    *   Test edge cases:
        *   Job with very few steps.
        *   Job with no badput events logged (goodput should be ~100%).

4.  **Test `--logger_name` Argument:**
    *   If a custom `logger_name` was used during event generation, test the CLI using the `--logger_name` argument instead of relying on `job_name` derivation.

5.  **Verify JSON Output (Manual Check):**
    *   Temporarily uncomment the JSON export section in `new_goodput_calculator_cli.py`.
    *   Run the script and inspect the generated JSON file for correctness and completeness of data.

**Success Criteria:**
*   The CLI executes without errors for valid job names/logger names with existing data.
*   Calculated goodput, badput breakdown, and timeline information are accurate and consistent with the logged event data.
*   Edge cases are handled gracefully.

## 5. Comparison with Old System (Optional)

**Objective:** Qualitatively compare the new goodput metrics with any available baseline metrics from the old system.

**Actions:**
1.  **Identify Comparable Metrics:** If the old system produced a goodput percentage or identified similar sources of inefficiency, note these down.
2.  **Run Parallel Tests (if feasible):** For a limited set of training jobs, run both the old and new goodput measurement systems (if possible without interference).
3.  **Qualitative Comparison:**
    *   Compare the overall goodput percentages. Are they in a similar range for similar jobs?
    *   Do both systems identify similar major sources of inefficiency?
    *   Note any significant discrepancies and investigate if they point to improvements in the new system (e.g., more accurate measurement) or potential issues.

**Note:** This is a qualitative comparison. The new system may define "goodput" and "badput" differently or measure them more granularly, so exact matches are not expected. The goal is to ensure the new system provides at least as much, if not more, useful insight.

**Success Criteria:** The new system provides goodput metrics that are comprehensible and appear to reflect job performance, ideally offering more detailed insights than the old system.

## 6. Expected Outcomes (Overall Success Criteria)

A successful testing phase for the goodput measurement migration is defined by:

1.  **Library Stability:** The `ml-goodput-measurement` library's unit tests all pass.
2.  **Correct Event Logging:** `GoodputRecorder` accurately logs all specified training lifecycle events with correct data to the designated backend.
3.  **Accurate Calculation & Reporting:** `new_goodput_calculator_cli.py` correctly processes these events and reports goodput/badput metrics that are consistent with the input data.
4.  **Improved Insights:** The new system provides clear, actionable insights into training efficiency and sources of badput.
5.  **Documentation Utility:** The integration guide (`GoodputRecorder_Integration_Guide.md`) and the CLI script template (`new_goodput_calculator_cli.py`) are proven useful and accurate through this testing process.
